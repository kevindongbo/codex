## 4. 需求二：修复 ERP 订单取消 HTTP 500

### 4.1 已确认业务语义

- “取消”只停止 ERP 内部履约，不调用 TikTok、Shopee、Ozon 等平台 API 取消买家订单。
- 未锁库订单取消后直接进入 ERP 已取消状态。
- 已锁库订单取消时，必须在同一数据库事务中释放全部有效 reservation。
- 已出库订单禁止取消，返回清楚的 4xx 业务错误。
- ERP 人工取消不能被后续平台同步自动恢复。
- 需要恢复时由用户点击“恢复履约”；恢复后清空仓库，不恢复旧 reservation，重新选择仓库并重新锁库。

### 4.2 必须真实定位

针对截图中的订单取消操作，记录：

```text
操作时间
订单号和订单 ID
请求方法与 URL
请求负载
HTTP 状态码
响应摘要
同一时间段 Gunicorn/Django 日志堆栈
数据库中订单、订单行、StockReservation、StockBalance、StockLedger 状态
```

重点排查但不提前假定根因：

- 历史订单没有仓库或订单明细；
- `quantity_reserved` 与有效 `StockReservation` 不一致；
- 旧数据缺少新迁移字段；
- 释放流水的幂等键或关联字段冲突；
- 序列化返回阶段异常；
- 前端成功后全量刷新中的其他接口失败。

如果发现历史数据不一致，不允许静默篡改库存。应提供只读诊断命令和可审查的修复 migration 或 management command。

### 4.3 前端行为

1. 用户点击“取消”。
2. 显示二次确认。
3. 用户确认后只发送一次取消请求，按钮进入处理中并禁止重复点击。
4. 成功后立即更新订单状态和库存锁定数量。
5. 失败时显示后端返回的业务错误；500 需要显示可用于关联日志的请求标识，不只显示“请稍后重试”。

### 4.4 验收场景

- DRAFT/READY 取消成功。
- ALLOCATED/PICKING/VERIFIED 取消成功并原子释放锁库。
- SHIPPED 返回明确的 4xx，库存不变。
- 双击或重复请求不会重复释放。
- 取消后平台同步不恢复 ERP 履约。
- 恢复履约后必须重新选仓、重新校验和重新锁库。
- 覆盖真实前端链路：点击 → 确认 → API 一次 → reservation 释放 → UI 更新。

## 6. 需求四：统一采购在途与调拨在途

### 6.1 已确认口径

库存列表中的“在途库存”必须为：

```text
采购在途剩余数量
+ 调入本仓的仓间调拨在途剩余数量
```

示例 SKU `AI-BAG-BROWN-05`：

```text
采购单 PO-20260805-2715：在途 150
仓间调拨：在途 95
库存列表应显示：245
```

当前显示 95 为错误，因为只展示了调拨在途。

### 6.2 状态边界

- 采购页面已经标为“在途”的数量必须进入库存列表的在途合计。
- 采购草稿不计入在途。
- 已取消、已收货或异常关闭的数量不计入剩余在途。
- 调拨只计入目的仓，不计入来源仓。
- 采购收货：对应采购在途减少，目的仓 `on_hand` 增加。
- 调拨收货：对应调拨在途减少，目的仓 `on_hand` 增加。
- 异常关闭：在途减少，但不增加 `on_hand`，也不恢复来源仓库存。
- 不得同时从余额字段和业务单据重复相加，避免双重计算。

### 6.3 在途来源明细

库存列表的在途数字应支持点击查看来源，至少显示：

```text
来源类型：采购 / 仓间调拨
来源单号
物流单号（如有）
原计划数量
已收数量
异常关闭数量
剩余在途数量
发出/确认时间
预计到货时间（如有）
```

来源明细剩余数量之和必须严格等于库存列表显示的合计。

### 6.4 全页面统一

以下位置必须使用同一口径：

- 仓配中心顶部“在途数量”；
- 库存列表“在途库存”；
- 智能补货“可用 / 在途”；
- 补货算法 `inventory_position`；
- 在途来源详情。

示例中应保持：

```text
可用：7
在途：245
库存位：252
```

不能再出现库存列表 95、补货库存位 252，却无法解释中间 150 的情况。

## 7. 需求五：创建订单改为可视化 SKU 卡片选择

### 7.1 页面风格

参考现有“创建采购单”的商品卡片选择方式，创建订单弹窗增加：

- SKU/商品名称搜索；
- 商品图片；
- 商品名称；
- SKU 编码；
- 当前履约仓库；
- 可用库存；
- 订单数量输入；
- 加入明细按钮；
- 已加入明细列表与移除操作。

仅显示已启用、可用于订单的本店 SKU；图片加载失败使用现有占位图逻辑。

### 7.2 库存不足规则

- 库存不足的 SKU 仍允许加入订单。
- 卡片上必须醒目标明可用量和预计缺口。
- 创建时整单库存不足，订单仍保存为“库存不足”。
- 库存不足时不得部分锁库、不得部分扣库、不得生成部分出库流水。
- 后续库存充足后，用户可重新选择仓库并整单锁库/出库。

### 7.3 一次确认出库

用户在创建订单弹窗只点击一次“确认并出库”：

- 整单库存充足：在一个原子流程中保存订单、校验、锁库、扣库并完成出库。
- 整单库存不足：保存订单为“库存不足”，整单不锁库、不扣库。
- 请求重试不得创建重复订单、重复 reservation 或重复出库流水。
- 成功与库存不足必须返回不同、清楚的结果，前端显示对应状态。

### 7.4 验收场景

- 搜索 SKU 和商品名均能找到商品。
- 卡片显示真实图片、名称、SKU 和当前仓可用库存。
- 多 SKU 可加入同一订单，重复加入合并数量或明确阻止重复行。
- 一行缺货时整单保存为库存不足，所有 SKU 均不扣库。
- 全部充足时一次点击完成整单出库。
- 刷新页面后订单状态和明细保持正确。

## 8. 需求六：修正日均出库算法

### 8.1 已确认公式

```text
销售出库总量
= 订单实际出库数量
+ 手动出库数量
- 对应销售订单的退货数量
```

退货必须回溯扣减到原订单销售日期，不记在实际退货入库当天。

### 8.2 纳入与排除

纳入：

- 订单确认出库生成的最终出库流水；
- 手动出库流水；
- 与原销售订单关联的退货，按原销售日扣减。

排除：

- 锁库与释放锁库；
- 仓间调拨出库；
- 盘亏、报损；
- 普通库存调整；
- 已撤回/已冲销流水；
- 未完成出库的订单。

### 8.3 时间窗口

- 3、7、15、30 天窗口使用同一业务口径。
- 每个窗口按完整自然时间跨度除以对应天数，不只除以有销量的天数。
- 加权日均继续使用组织配置的窗口权重。
- 仓库与 SKU 必须分别计算，不能跨仓混算。

### 8.4 已定位代码缺口

当前后端说明写明应统计订单出库和手动出库，但查询只筛选订单出库事件，导致通过“手动出库”录入的销售全部被遗漏。必须修正查询、退货回溯和测试。

### 8.5 解释性 UI

“查看周期明细”至少显示：

```text
3/7/15/30 天订单出库
3/7/15/30 天手动出库
3/7/15/30 天退货回溯扣减
各窗口净销售量
各窗口日均
最终加权日均
```

如果最终为 0，应明确显示原因，例如“近 30 天没有订单或手动销售出库”，不能只显示无解释的 `0.00`。
