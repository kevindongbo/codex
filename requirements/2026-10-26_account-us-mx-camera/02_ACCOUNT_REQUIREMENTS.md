# 账号归档与恢复需求

关联决策：D-01。目标是让离职人员从日常管理中退出，同时保留业务责任归属，不执行物理删除。

## 1. 生命周期

就业状态与登录状态分开：`employment_status=employed/departed`；原 `active` 继续表示账号启用状态。组合仅允许：在职启用、在职停用、已离职停用。禁止“已离职启用”。

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 在职启用／在职停用 | 移入已离职 | 就业状态departed；User和Membership停用；记录离职信息；令牌代际递增 |
| 已离职 | 再次归档同一版本／幂等请求 | 返回第一次结果，不重复审计或重复改变离职时间 |
| 已离职 | 恢复为在职 | 就业状态employed，但仍停用；令牌代际再次递增；不恢复旧会话、管理员角色或仓库授权 |
| 恢复后在职停用 | 主账号设置新密码、审核权限并启用 | 新会话可登录，原 token 永久失效；是否加入排班需显式选择 |
| 已离职 | PATCH active=true、旧客户端“启用” | 409 `account_departed`，提示先走恢复流程 |
| 任意 | 物理删除User／Membership | 本期不提供入口、不实现该操作 |

恢复不是“自动回到离职前状态”。保留离职前角色及授权的只读审计摘要供主账号参考；恢复后的执行角色为viewer、权限显式为`["view"]`、仓库授权空、排班参与停用。必须避免“空权限列表继承admin默认权限”的现有语义陷阱。

## 2. 权限与保护（A-10）

- 只有当前组织的主账号可看账号管理、归档和恢复。普通admin/manager/buyer/warehouse/viewer均由后端返回403。
- 主账号本人、任何超级用户不得在此流程中归档或恢复；保护在后端强制执行，不依靠前端隐藏按钮。
- 账号ID使用Membership UUID并验证组织归属；不存在／异组织返回404，避免暴露其他组织身份。
- 保留用户名唯一性，离职后不把同名新员工绑定到旧User；历史记录不得自动“认领”给新人。
- 不允许归档接口携带 role、permissions、warehouse_ids、password 等无关字段；未知字段拒绝，不静默扩权。

## 3. 归档流程（A-11）

1. 在“在职人员”或“已停用”列表点击“移入已离职”。
2. 后端预检返回当前revision、显示名、角色、启用状态，以及未完成采购／订单／跟进的**数量**和未来排班的影响摘要；不返回敏感课表原图或私有原因。
3. 确认弹窗清楚说明：立即禁止登录；从新采购人及未来排班选择移除；历史记录保留；待办不会自动改负责人。离职日期默认当前业务日期，可填写过去日期但不能用将来日期伪装预约功能。
4. 离职原因选填，最大500字符，仅主账号及受控审计可见。点击确认才发送写请求，取消不写入。
5. 单事务锁组织、Membership、User及安全状态，重新验证revision和保护条件，更新就业状态／访问状态、增加token generation、暂停排班参与并写审计、增加同步版本。
6. 已知待办不阻止立即收回访问；显著提示需要交接，保留原责任人，不能静默转派给主账号。自动任务不得继续代表离职人员执行新的有偿操作。
7. 成功后将该行从日常列表移到“已离职”；总数更新，其他客户端收到同步版本后刷新。

同一用户的关键业务写事务应与归档采用一致的组织锁顺序，取得锁后再次确认操作者有效身份／状态，避免请求通过最初鉴权后等待期间已被归档却仍继续写入。已在归档前提交的业务保留；不能承诺撤回所有已在外部发出的网络请求。并发规则及限制须在安全回归中验证。

## 4. 会话失效（A-12）

仅设置is_active不能证明“恢复后旧token不会再用”。建议增加每个User唯一的`AccountSecurityState.auth_version`，新access/refresh均签入同一`auth_version`。

- 每次验证access时核对User启用、有效Membership、非离职及token版本；刷新时同样核对数据库状态，不能只验证refresh签名和过期时间。
- 归档与恢复都递增版本，旧access、旧refresh在恢复后仍401；恢复并启用后必须重新登录获得新版本。
- 兼容既有未带版本token：仅在数据库版本为0且账号仍在职启用时允许；归档过的账号不能回落到0。上线不可让全员意外退出，主账号会话必须单独回归。
- 已离职账号即使知道原密码也不能登录；恢复流程要求主账号设置新密码后再启用。密码仅write-only，不进入审计、日志或响应。
- 前端401只触发一次共享刷新；刷新明确失败后清除有效会话并提示重新登录，保留可恢复的未提交草稿，阻止后台自动重试写入。403显示权限不足，不能用重登录解决授权问题。
- 离职人员持有的后台任务授权在执行前重新校验。排队中的个人课表识别标记失败`account_departed`，不调用模型；处理中的结果在落库前检查状态并丢弃候选，不发布排班。历史成功结果不删除，恢复不自动重跑旧任务。

## 5. 人员与历史联动（A-13）

| 场景 | 归档后行为 |
| --- | --- |
| 新建采购单、接收新任务的负责人选择 | 不显示已离职人员；后端拒绝将其作为新负责人 |
| 编辑历史采购／订单但未更换负责人 | 原负责人仍显示“姓名（已离职）”，不能因下拉中缺少而自动清空或改成当前人 |
| 历史库存流水、审计、利润方案、达人跟进 | 保留ID和原责任归属；不影响库存数量、已计算金额及版本 |
| 当前及未来共享排班 | 不再计入可上班人员、待交课表提醒；原始班表／课程格不批量删改 |
| 已开始的历史排班 | 继续可追溯；原图、历史版本及本人私密内容仍按原权限保护 |
| 恢复人员 | 不自动恢复仓库、管理员权限、排班参与或旧任务；主账号重新审核 |

上述历史展示应尽可能使用已有业务快照；若显示名以后改变，不能把“当前显示名”当成“当时签名”。本期不批量重写既有快照。

## 6. UI 与无障碍（A-14）

- 账号管理顶部：搜索框；“在职人员／已停用／已离职／全部”筛选及数量；新增账号按钮。
- 日常默认只显示在职人员（含在职停用，可按启用状态过滤）。每行首先显示姓名、账号、角色、状态；仓库和权限使用摘要+展开，不再把全部权限堆成一段小字。
- 在职行动：编辑、启用／停用、移入已离职。离职行动：查看历史信息、恢复为在职；不出现直接“启用”。
- 归档和恢复各有独立确认步骤，展示操作对象和后果，按钮加载时禁止重复提交。恢复明确显示“恢复后仍停用，需要重新设置密码与授权”。
- 桌面列表与手机卡片保持相同操作语义；390px无整页横滚；弹窗焦点约束、Esc取消、关闭后回到触发按钮；错误文字可读且不只依赖颜色。

## 7. 数据兼容和审计

旧active=false人员迁移为“在职停用”，不能直接推断离职；由主账号逐个归档。审计记录归档/恢复操作者、目标ID、时间、revision、前后状态、权限摘要及原因，不记录密码、JWT、密钥或完整请求。

归档需要可逆的状态恢复路径，不需要恢复数据库备份。数据库结构回滚不能物理删除新产生的离职审计与会话代际；先禁写、保留新字段和审计，再回退兼容代码。详见 [数据与迁移](05_DATA_API_MIGRATION.md)。
