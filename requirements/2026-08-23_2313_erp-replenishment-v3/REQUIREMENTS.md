## 0. 开发原则

这不是重写 ERP，而是在现有采购、库存、StockLedger、调拨和智能补货模块上做兼容性修正。

开发必须遵守：

- 先读现有代码、模型、migration、测试，再改。
- 后端是补货计算唯一真值；前端不要维护一套不同公式。
- 保留历史数据和旧 recommendation snapshot；新推荐使用新的 calculation version。
- 所有 schema 变化必须有 migration。
- 不直接改主分支。
- 修改完成后必须运行 ERP 相关后端/前端测试，并特别验证采购、调拨、库存流水回归。

建议新 calculation version：`v3_all_warehouse_primary_warehouse`。

# 1. 当前状态核对

## 1.1 调拨运输异常关闭

**状态：已开发但有接口 Bug，需要修改。**

后端 `TransferExceptionCloseInputSerializer` 继承了包含 `idempotency_key` 的输入结构，但前端 `closeTransferException()` 只发送 `quantities` 和 `reason`，导致页面报：

`idempotency_key：该字段是必填项。`

要求：

- 前端异常关闭使用与调拨发出/收货相同的幂等模式生成 `idempotency_key`。
- 成功/失败都正确调用现有幂等完成逻辑。
- 不允许通过删除后端幂等校验来“修复”。

## 1.2 智能补货基础能力

**状态：基础框架已存在，但核心口径需要重构。**

现有系统已有：

- 3/7/15/30 日权重全局设置；
- `ReplenishmentPolicy`；
- `ReplenishmentRecommendation`；
- 库存余额 / 在途；
- 到货周期估算；
- 批量调整参数；
- 补货表格和推荐结果。

但当前实现仍有以下问题：

- 需求主要按单仓计算，而不是全仓；
- 当前加权方法先把每个窗口除以天数，再加权，与本需求公式不同；
- 当前会扣客户退货；
- 人工 lead override 优先于历史 P80；
- 安全库存、波动安全量、安全余量等混在最终目标里；
- review cycle 可编辑且默认 7 天；
- 起订量/整箱数默认 1，不能真正留空；
- 没有完整的 SKU 级“主力仓库 + SKU 独立权重”模型。

# 2. 调拨异常关闭业务规则

示例：学校仓发出 100 件到广州仓，广州仓实际收到 80 件，剩余 20 件运输异常。

异常关闭 20 件以后：

- 学校仓不恢复这 20 件；
- 广州仓不增加这 20 件；
- 剩余 20 件从调拨在途中清零；
- 调拨记录保留 `received_quantity = 80`；
- 调拨记录保留 `exception_closed_quantity = 20`；
- 保存异常原因；
- 历史可追溯；
- 同一幂等键重复请求不得产生二次库存影响。

定义：**异常关闭是对已经发出的运输异常数量做最终结案，不是撤销调拨。**

必须新增/补全测试：

1. 发出 100：来源仓减少 100，目标仓在途 100。
2. 收到 80：目标仓增加 80，在途剩 20。
3. 异常关闭 20：目标仓不增加、来源仓不恢复、在途归零、异常数量和原因保存。
4. 同一 `idempotency_key` 重试结果稳定、无重复流水。
5. 前端请求 body 必须包含 `idempotency_key`。

# 3. 智能补货总体原则

智能补货页面继续按仓库查看，不改成全局 SKU 单表。

但计算维度强制拆成：

- **需求侧：全仓。**
- **库存侧：主力仓。**

这是 V3 的核心原则。

# 4. SKU 主力仓库

## 4.1 每个 SKU 可设置一个主力仓库

需要持久化的 SKU 级主力仓字段/配置，例如 `primary_replenishment_warehouse`，不得只存在前端。

可以新增 `SKUReplenishmentProfile` 一 SKU 一条，或在评估 migration 风险后采用等价的最小改动方案。重点是以下参数必须是 SKU 级，而不是同一 SKU 在每个仓库各有一套：

- 主力仓库；
- 3/7/15/30 独立权重 override；
- 目标覆盖天数；
- 固定安全库存；
- 人工到货周期 fallback；
- 起订量；
- 整箱数。

## 4.2 单个/批量设置

复用现有单选、多选、全选、批量调整参数。

主力仓支持：

- 单个 SKU 设置；
- 多 SKU 批量设置；
- 全选后批量设置。

批量修改必须是“字段级 patch”：只更新用户明确选择修改的字段，其他配置完全保持原值。

## 4.3 切换主力仓

主力仓从学校仓改成广州仓后，以下 SKU 配置保持不变：

- 权重；
- 目标覆盖天数；
- 固定安全库存；
- 起订量；
- 整箱数。

重新按新主力仓计算：

- 预测到货周期；
- 可用；
- 已确认在途；
- 可售天数；
- 最迟下单；
- 建议补货；
- 紧急度。

# 5. 页面归属规则

## 5.1 已设置主力仓

如果 SKU 主力仓 = 广州仓，则该 SKU **只显示在广州仓智能补货页**，不再出现在其他仓库补货页。

主表不需要额外增加“主力仓”列；主力仓在调整参数中维护。

## 5.2 未设置主力仓

未设置主力仓的 SKU 在所有仓库智能补货页都可以看到，便于用户找到并配置。

可以显示：

- 商品；
- 全仓加权日均出库；
- 近 30 天出库来源；
- 当前页面仓库的可用 / 在途；
- 当前页面仓库预测到货周期；
- 可售天数。

但以下三个字段不得输出正式判断，统一显示 **“请先设置主力仓库”**：

- 最迟下单；
- 建议补货；
- 紧急度。

避免同一 SKU 在多个仓同时出现“立即补货”。

# 6. 全仓需求口径

无论当前打开哪个仓库页面，Q3/Q7/Q15/Q30 都统计该 SKU **所有仓库**的真实出库总和。

计入需求的 StockLedger 类型只包括：

- `SHIPMENT`：销售订单正式出库；
- `MANUAL_OUTBOUND`：手动出库。

不计入其他库存动作，包括但不限于：库存调整/报损/盘亏、调拨发出/收货/在途、采购相关、手动入库、锁定/释放等。

被撤销/冲销的原出库不得重复计入。

## 6.1 客户退货

客户退货 **不反向扣减历史需求**。

例如：发货 100，后续退货 20，需求仍记 100，不是 80。

---

# 7. 全仓加权日均出库公式

设：

- Q3 = 近 3 天全仓总出库量
- Q7 = 近 7 天全仓总出库量
- Q15 = 近 15 天全仓总出库量
- Q30 = 近 30 天全仓总出库量
- W3/W7/W15/W30 = 对应权重

强制公式：

`weighted_daily_outbound = (Q3*W3 + Q7*W7 + Q15*W15 + Q30*W30) / (3*W3 + 7*W7 + 15*W15 + 30*W30)`

**禁止**使用：

`(Q3/3)*W3 + (Q7/7)*W7 + (Q15/15)*W15 + (Q30/30)*W30`

默认 40/30/20/10 时加权天数分母是 9.3，但 **9.3 禁止硬编码**，必须随权重动态计算。

---

# 8. 权重体系

采用：**全局默认 + SKU 独立覆盖**。

## 8.1 全局默认

默认：

- 3 天 40%
- 7 天 30%
- 15 天 20%
- 30 天 10%

现有全局字段可以继续复用。

## 8.2 SKU override

SKU 未设置 override：继承全局权重。

SKU 设置 override：只使用自身权重。

支持单个、多选、全选批量设置。

## 8.3 校验

四项权重合计必须 **严格等于 100%** 才允许保存，不自动 normalize。

错误提示建议：`3/7/15/30 天权重合计必须为 100%。`

## 8.4 恢复全局

提供“恢复全局权重”，实际语义是清除 SKU override。以后全局权重变化时，该 SKU 自动跟随。

# 9. 近 30 天出库来源

计算口径与需求一致：近 30 天 `SHIPMENT + MANUAL_OUTBOUND`，不扣退货，按真实 StockLedger warehouse 分组。

主表只显示合计，例如：`680 件`。

点击合计后用小 Popover / Modal 显示：

- 学校仓 420

- 马来仓 80
- 合计 680

# 11. 库存侧只看主力仓

一旦 SKU 设置主力仓，所有补货库存计算只使用主力仓。

例如广州主力仓 50 件、学校仓 500 件：智能补货库存侧只用广州仓 50，学校仓 500 不抵扣广州仓采购建议。

## 11.1 可用

`available = on_hand - reserved`

## 11.2 已确认在途

建议补货的库存位需要计入会实际进入主力仓的已确认在途，包括：

- 已确认采购在途；
- 已发出/确认、目标为主力仓的调拨在途。

不计入：

- 草稿/未确认/已取消采购；
- 草稿/未发出调拨；
- 已异常关闭数量；
- 已撤销动作。

# 12. 可售天数

页面可售天数：

`available_days_cover = 主力仓可用库存 / 全仓加权日均出库`

**不包含在途。**

例如可用 200、在途 300、日均 20，可售天数 = 10 天，不是 25 天。

# 13. 预测到货周期

恢复历史优先逻辑，针对 `SKU + 主力仓`：

1. 历史完整收货周期 P80；
2. 若无足够完整收货数据，使用首次收货周期 P80；
3. 若无可用历史，使用 SKU 人工到货周期 fallback；
4. 再无则用系统默认 fallback。

历史样本阈值、P80 算法优先复用现有已实现逻辑，不另造统计方法。

页面来源标签：

- 历史完整收货 P80
- 历史首次收货 P80
- 人工周期
- 系统默认

人工周期不能无条件覆盖成熟历史数据。

# 14. 目标覆盖天数与安全库存模式

目标覆盖天数是 SKU 参数：

- 默认 30 天；
- 可手工修改；
- 可清空。

两种模式必须互斥。

## 14.1 模式 A：目标覆盖模式

条件：`target_coverage_days != null`

`effective_coverage_days = max(predicted_lead_days, target_coverage_days)`

`target_inventory = weighted_daily_outbound * effective_coverage_days`

此模式禁止额外叠加：

- SKU 固定安全库存；
- safety_days；
- volatility safety；
- service_level_factor；
- safety_margin_ratio；
- 其他隐藏余量。

旧字段可为兼容历史保留，但 V3 最终补货计算必须脱钩。

## 14.2 模式 B：固定安全库存模式

条件：`target_coverage_days == null`

`target_inventory = weighted_daily_outbound * predicted_lead_days + sku_fixed_safety_stock`

固定安全库存属于 SKU，切换主力仓不清空。优先评估复用已有 SKU `safety_stock`，不要无必要创建同义字段。

# 15. 补货触发与补货目标分离

不能只因为库存低于目标覆盖就持续建议采购。必须先达到触发点。

定义库存位：

`inventory_position = 主力仓可用 + 主力仓已确认在途`

注意：库存位包含在途，但页面“可售天数”不包含在途。

## 15.1 目标覆盖模式触发

`trigger_point = weighted_daily_outbound * predicted_lead_days`

只有：

`inventory_position <= trigger_point`

才触发补货。

触发后：

`raw_suggested_qty = max(target_inventory - inventory_position, 0)`

未触发：`suggested_qty = 0`，页面显示“暂不补货”。

示例：日均 20、lead 15、coverage 30：

- 触发点 = 300
- 目标库存 = 600
- 库存位 350 → 未触发，建议 0
- 库存位 280 → 触发，基础建议 320

## 15.2 安全库存模式触发

`trigger_point = weighted_daily_outbound * predicted_lead_days + sku_fixed_safety_stock`

该模式 `target_inventory == trigger_point`。

示例：日均 20、lead 15、安全库存 100：触发点/目标 = 400。库存位 350 时基础建议 = 50。

# 16. 起订量与整箱数

UI 禁止出现 `MOQ`，统一名称：**起订量**。

## 16.1 起订量

允许为空。

- 空：无最低采购限制。
- 设置 100，基础建议 60 → 100。
- 设置 100，基础建议 230 → 230（起订量不把 230 放大成 300）。

## 16.2 整箱数

允许为空。

- 空：237 → 237。
- 设置 50：237 → 250。

## 16.3 同时存在

顺序：

1. 计算基础建议量；
2. 若设置起订量且基础建议低于起订量，先提升到起订量；
3. 若设置整箱数，再向上取整到整箱数倍数。

示例：基础 60、起订量 100、整箱 50 → 100。  
示例：基础 230、起订量 100、整箱 50 → 250。

现有 `min_order_qty=1`、`pack_size=1` 不应继续用 1 冒充“未设置”。修改模型/校验，使其真正可 null/blank。

历史 migration：旧默认 1 优先迁移成 null（未设置），除非存在可靠审计可以证明用户明确设置为 1；不要仅按数值猜用户意图之外的复杂情况。

---

# 17. 最迟下单日

先计算基于库存位的预计耗尽天数：

`depletion_days = (主力仓可用 + 已确认在途) / weighted_daily_outbound`

`latest_order_date = 当前日期 + depletion_days - predicted_lead_days`

禁止再额外减：

- safety_days；
- review_cycle_days；
- safety margin。

当 `weighted_daily_outbound <= 0` 时显示“暂无”。

---

# 18. 检查周期和自动重算

移除用户可编辑的“检查频率/复核周期”。V3 固定：**每天检查一次**。

采用双机制：

1. **后台每日自动检查**：用户不打开 ERP 也必须更新补货状态。复用项目现有后台任务/定时机制，在低峰时间执行，不为本需求重复引入新的调度框架。
2. **实时重算/失效**：页面打开或关键库存/策略事件发生后，相关 SKU 立即刷新。

至少覆盖事件：

- 销售出库；
- 手动出库；
- 库存调整；
- 采购确认/收货/取消；
- 调拨发出/收货/异常关闭/取消；
- 主力仓修改；
- 权重修改；
- 目标覆盖修改；
- 安全库存修改；
- 起订量/整箱数/人工 lead fallback 修改。

现有 `review_cycle_days` 等旧字段先保留兼容历史，但 V3 计算与 UI 不再依赖/暴露。

# 21. 计算测试用例

必须有后端自动化测试覆盖：

### Case A：强制加权公式

Q3=60，Q7=120，Q15=240，Q30=400，W=40/30/20/10。

必须：

`(60*0.4 + 120*0.3 + 240*0.2 + 400*0.1) / (3*0.4 + 7*0.3 + 15*0.2 + 30*0.1)`

不得先分别除 3/7/15/30。

### Case B：退货不扣需求

出库 100，退货 20，需求 = 100。

### Case C：报损/调整不计需求

销售出库 100 + 手动出库 20 + 报损/调整 30，需求 = 120。

### Case D：多仓需求

学校 100 + 广州 200 + 马来 50 = 全仓 350。无论打开哪个仓页，需求窗口总量都使用 350。

### Case E：库存只看主力仓

主力仓广州 50，学校仓 500，补货库存只用广州仓。

### Case F：目标覆盖未触发

日均 20，lead 15，coverage 30，库存位 350：触发点 300，目标 600，建议 0。

### Case G：目标覆盖已触发

同上库存位 280：基础建议 320。

### Case H：安全库存模式

coverage=null，日均 20，lead 15，安全库存 100，库存位 350：触发点=目标=400，基础建议 50。

### Case I：起订量

基础建议 50，起订量 100，整箱空 → 最终 100。

### Case J：整箱

基础 237，起订量空，整箱 50 → 最终 250。

### Case K：起订量 + 整箱
