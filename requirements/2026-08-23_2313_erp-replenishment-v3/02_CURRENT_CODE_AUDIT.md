# ERP 智能补货 V3 + 调拨异常关闭：当前代码审计

- 业务真值：`01_FULL_REQUIREMENTS.md`

> 目的：让 Codex 在动手前明确“现有代码有什么、哪里与新需求冲突、哪些必须复用”。开发时仍需重新读取实际最新代码，不得只依赖本审计文档。

## 1. 调拨异常关闭

### 当前状态：已开发但有接口 Bug，需要修改

- 后端已有 `TransferExceptionCloseInputSerializer`，继承了要求 `idempotency_key` 的输入结构。
- 前端 `team.js` 的 `closeTransferException()` 当前只提交 `quantities + reason`，没有提交 `idempotency_key`。
- 因此前端会收到 `idempotency_key：该字段是必填项`。
- 修复必须沿用现有 `idempotencyKey(...) / completeIdempotency(...)` 模式，不得取消后端幂等校验。
- 异常关闭现有库存语义应保留：来源仓不恢复、目标仓不增加、剩余在途清零、异常数量和原因可追溯。

## 2. 需求速度 / 日均出库

### 当前状态：需要重构

当前 `backend/apps/erp/replenishment.py` 主要按单仓统计需求，并对 3/7/15/30 各窗口先计算日均后再加权；同时会把客户退货从需求中扣减。

新需求要求：

- Q3/Q7/Q15/Q30 全部按全仓汇总；
- 只计 `SHIPMENT + MANUAL_OUTBOUND`；
- 客户退货不反向扣需求；
- 公式必须是“加权总出库 / 加权天数”，禁止先除天数再加权。

## 3. 全局权重

### 当前状态：已有，可复用并扩展

现有 `ReplenishmentSettings` 已有：

- `velocity_weight_3`
- `velocity_weight_7`
- `velocity_weight_15`
- `velocity_weight_30`

默认值就是 40% / 30% / 20% / 10%。

需要新增 SKU 级 override，并支持“恢复全局权重”。四项保存时必须严格合计 100%，不得自动归一化。

## 4. 补货策略维度

### 当前状态：模型维度与新需求不完全一致

现有 `ReplenishmentPolicy` 是 `organization + warehouse + sku` 维度。

新需求中下列参数本质属于 SKU：

- 主力仓库；
- SKU 独立权重；
- 目标覆盖天数；
- 固定安全库存；
- 人工到货周期 fallback；
- 起订量；
- 整箱数。

Codex 应选择迁移风险最低的实现方式，优先新增 SKU 级 profile 或等价结构，避免同一 SKU 在每个仓库存多套互相冲突的参数。

## 5. 主力仓

### 当前状态：未完整实现，需要新增持久化字段/模型

当前 `SKU` 本身没有主力仓字段。

需要支持：

- 单 SKU 设置；
- 多选批量设置；
- 全选批量设置；
- 有主力仓时 SKU 只显示在该仓补货页；
- 无主力仓时所有仓页可见，但不输出正式补货决策。

## 6. 库存与在途

### 当前状态：已有库存基础结构，可复用

现有 `StockBalance` 已有：

- `on_hand`
- `reserved`
- `purchased_pending_shipment`
- `in_transit`
- `available = on_hand - reserved`

新逻辑必须明确：

- 可售天数只用主力仓 `available`；
- 补货库存位用主力仓 `available + 已确认采购在途 + 已确认调拨在途`；
- 其他仓库存不得抵扣主力仓补货。

## 7. 预测到货周期

### 当前状态：存在回归，需要恢复历史优先

现有代码近期使用 `manual_is_final=True`，导致人工 lead override 优先于历史数据。

新需求恢复为：

1. SKU + 主力仓完整收货历史 P80；
2. 无完整收货时使用首次收货 P80；
3. 无历史时人工周期 fallback；
4. 再无时系统默认 fallback。

## 8. 目标库存 / 安全库存

### 当前状态：旧公式与新需求冲突，需要重构

当前算法仍混入安全天数、波动安全量、service level、安全余量等。

新版本强制两种互斥模式：

- 目标覆盖天数有值：只按 `max(lead, coverage)` 计算目标库存，不叠加安全库存或其他余量；
- 目标覆盖天数为空：按 `日均*lead + SKU固定安全库存`。

旧参数可为兼容保留字段，但不得继续影响 V3 最终建议数量。

## 9. 补货触发

### 当前状态：需要按新逻辑拆分“触发点”和“目标库存”

- 目标覆盖模式触发点：`日均 * lead`；
- 安全库存模式触发点：`日均 * lead + 固定安全库存`；
- 未触发时建议补货必须为 0；
- 触发后才用 `target_inventory - inventory_position` 计算基础建议量。

## 10. 起订量 / 整箱数

### 当前状态：需要修改数据约束

现有 `min_order_qty`、`pack_size` 默认 1 且要求大于 0，不能真正表示“未设置”。

新需求：

- UI 统一使用中文“起订量”，不显示 MOQ；
- 起订量可空；
- 整箱数可空；
- 只有实际设置时才参与数量修正；
- 旧默认值 1 应优先迁移为“未设置”，除非有可靠证据是用户显式设置。

## 11. 检查频率 / 自动任务

### 当前状态：需要修改

现有全局和 Policy 中存在可编辑 `review_cycle_days`，默认 7 天。

新版本：

- 用户不再编辑检查频率；
- 固定每日后台自动检查一次；
- 页面打开和关键库存/采购/调拨事件发生后实时重算或使推荐失效。

应复用项目现有任务/定时机制，不为此单独引入不必要的新调度系统。

## 12. 前端表格

### 当前状态：需要调整

需要：

- checkbox 列缩窄；
- 商品列左移；
- “日均出库”改为“全仓加权日均出库”；
- 新增“近30天出库来源”；
- 周期详情和仓库来源详情用 Popover / Modal，禁止长 inline 展开撑高行；
- 主表不增加主力仓列，主力仓在参数调整中维护。

## 13. 后端作为唯一计算真值

### 当前状态：前端仍有本地 fallback 公式，需要统一

当前 `app.js` 有本地补货计算。V3 不允许前端长期维护一套与后端不同的公式。

优先：

- 后端返回完整可解释 snapshot；
- 前端只负责展示。

若开发模式必须保留 fallback，则公式必须与后端完全一致并有测试。

## 14. Migration / 历史兼容

### 当前状态：本次必然涉及 migration

预计至少涉及：

- SKU 级补货策略或主力仓字段；
- SKU 权重 override；
- 目标覆盖可空；
- 起订量可空；
- 整箱数可空；
- 旧默认值迁移。

不得破坏旧 `ReplenishmentRecommendation.snapshot`，新推荐建议使用新 `calculation_version`，例如 `v3_all_warehouse_primary_warehouse`。
