# 2026-10-28 数据显示故障修复

## 根因与证据

`0f814ef9` 引入的 PurchaseOrderSerializer 在初始化时执行
`if self.instance and self.instance.purchaser_id`。
DRF 的 `many=True` 会把分页列表或 QuerySet 传入子序列化器。
非空列表触发 `AttributeError: 'list' object has no attribute 'purchaser_id'`。
本地先运行回归测试复现失败，再用单实例类型判断修正；空采购列表无法暴露此缺陷。

TeamGateway.loadState 原来用 Promise.all 同时读取 18 个资源，任何一个失败就丢弃本轮所有结果。
初始商品、库存、店铺为空，仓库目录已经单独加载成功，因此出现“仓库仍在，所有业务数据归零”的页面。
同步标识只看是否能连接服务器，HTTP 500 也会显示“团队已同步”。
这些证据确认代码缺陷和故障链路，不代替生产数据库记录核查。

## 修复范围

- 只有 PurchaseOrder 单实例扩展原采购人选择范围，列表不访问单实例属性。
- 各资源独立结算，成功结果保留；失败资源使用当前会话上次成功的集合。
- 持续显示失败接口与 HTTP 状态，初次加载失败不再宣称完整同步。
- 数据不完整时阻止业务写请求，避免把未知库存当成零或重复录入。
- 至少间隔 15 秒重试失败加载，不依赖业务 revision 是否变化。
- 401/403 仍使读取失败，不通过缓存绕开权限。
- 更新静态资源版本号，避免旧脚本缓存。
- 发布新增主账号 JWT 的 19 个真实 GET 接口检查，仅打印路径、状态和数量。
- 历史校验增加商品、SKU、店铺原始字段的数量与哈希，既有库存、采购、人员、售价和利润历史继续校验。
- 识别旧应急脚本产生的唯一已知文件改动，备份后接入正式发布；未知本地修改一律停止。

## 数据与回退

没有新增迁移，没有清空、导入或恢复数据。正常发布仍先停写、备份 PostgreSQL、校验历史数据指纹；已有迁移再次执行应无待执行项目。
不得切回缺少账号认证代际检查的旧程序，亦不得逆向 0039。
发布后业务 GET 检查失败会保持维护状态并保留备份，不能报告发布成功。
已知应急改动在迁移前发布失败并回到旧 HEAD 时恢复；进入新版 schema 维护状态时保持新版代码。

## 验证

- 79 项 API 与针对性回归在隔离 PostgreSQL 中通过；首次缺少测试用加密配置后，使用进程内随机测试密钥重跑通过。
- 针对性回归覆盖非空分页采购、QuerySet 初始化、单采购编辑、离职采购人归属和库存保持。
- Node 测试覆盖首次/后续加载失败、缓存保留、只读保护、重试、授权拒绝、发布失败和已知应急改动处理。
- Edge 浏览器使用合成 HTTP 故障，验证桌面与手机提示、商品保留、重试恢复和再次故障；零 pageerror。
- 构建、Bash 语法及 diff 检查通过。

生产执行与页面恢复必须以实际终端输出和页面为准。此前的测试数量不构成生产验收证明。
